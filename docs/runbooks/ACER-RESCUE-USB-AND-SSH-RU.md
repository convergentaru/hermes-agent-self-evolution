# Acer Rescue: записать USB (если нужно), загрузить удалённый компьютер и подключиться по Tailscale + SSH

**Цель:** получить удалённую read-only диагностику Acer TravelMate P259, который показывает `No Bootable Device`.  
**Текущая рабочая гипотеза:** rescue ISO уже записан на USB. Поэтому сначала используется готовый носитель; повторная запись — только если обнаружен конкретный дефект.

## 0. Не перепутать этапы

- USB подключается к Acer **в удалённом городе**, а не обязательно к домашнему Ubuntu.
- Если образ уже записан и носитель исправен, повторно записывать его не нужно.
- Для удалённой работы требуется, чтобы rescue-система загрузилась, получила сеть, присоединилась к tailnet и запустила SSH/Tailscale SSH в соответствии с фактической конфигурацией проекта.
- Наличие ISO и успешная проверка QEMU **не доказывают**, что физический компьютер загрузился или что удалённый вход работает.
- До отдельного плана ремонта внутренний диск Acer не изменять: только читать сведения о накопителях и Windows-разделах.

## 1. На домашнем Ubuntu: проверить подготовку и сеть

Из терминала домашнего Ubuntu:

~~~bash
cd ~/projects/acer-rescue-usb || exit 1

echo '=== PROJECT STATE ==='
git status --short
git branch --show-current
git log -1 --oneline

echo '=== ISO FILES ==='
find . -maxdepth 4 -type f -iname '*.iso' -printf '%p\t%s bytes\t%TY-%Tm-%Td %TH:%TM\n'

echo '=== RESCUE V6 SHA-256 (если файл существует) ==='
if test -f build/acer-rescue-v6-final.iso; then
  sha256sum build/acer-rescue-v6-final.iso
else
  echo 'build/acer-rescue-v6-final.iso отсутствует; выбери существующий образ по манифестам и отчётам.'
fi

echo '=== HOME TAILSCALE ==='
tailscale status
tailscale ip -4
tailscale netcheck
~~~

Не публикуй серийные номера, auth keys, private keys, пароли или Tailscale auth URLs. Проверь фактические результаты, не додумывай их.

## 2. Человек у Acer: загрузить уже записанную флешку

Передай человеку на месте только эту короткую инструкцию:

1. Выключить Acer, вставить уже подготовленную rescue-флешку и включить компьютер.
2. Сразу нажимать **F12** для Boot Menu. Выбрать USB/UEFI-запись, соответствующую флешке.
3. Дождаться загрузки rescue-системы. Не выбирать установку Ubuntu и не запускать установщик/форматирование.
4. Если F12 не открывает меню, войти через F2 в BIOS и проверить только параметр **F12 Boot Menu**. Не менять режим SATA, Secure Boot, UEFI/Legacy или другие настройки наугад.
5. Если rescue-система не загрузилась или экран выглядит иначе, прислать фото экрана. Не менять внутренний диск и не выполнять repair.
6. После успешной загрузки оставить компьютер включённым и подключённым к доступной сети. Дальнейшую диагностику домашний оператор выполняет по Tailscale/SSH, как только узел появится.

**Не просить человека подключать USB к домашнему Ubuntu.** Флешка нужна у Acer.

## 3. Дождаться rescue-узла в Tailscale

На домашнем Ubuntu выполнить снова:

~~~bash
tailscale status
~~~

Найди только узел, который подтверждён конфигурацией rescue-проекта (ожидаемые hostname/имя и способ регистрации необходимо прочитать из текущих конфигов проекта). Не угадывай имя и не пробуй подключаться к посторонним узлам.

Если узел появился, проверь соединение:

~~~bash
tailscale ping <ПОДТВЕРЖДЁННОЕ_ИМЯ_ИЛИ_TAILSCALE_IP>
~~~

Подставь только фактически найденное имя/IP. Если узел не появляется, не переписывай ISO автоматически: сперва выясни по конфигурации, как rescue-система должна запускать сеть/Tailscale и как она получает право присоединиться к tailnet.

## 4. Подключиться по SSH

Изучи в `~/projects/acer-rescue-usb` реальную конфигурацию SSH: используется ли OpenSSH или Tailscale SSH, какое имя пользователя ожидается и как устроена авторизация. Не придумывай пользователя и не включай пароли/отключение host-key проверки наугад.

Когда подтверждены SSH user и адрес rescue-узла:

~~~bash
ssh -o ConnectTimeout=8 <ПОДТВЕРЖДЁННЫЙ_SSH_USER>@<ПОДТВЕРЖДЁННЫЙ_TAILSCALE_IP>
~~~

Если SSH спрашивает подтверждение ключа хоста, сравни ключ/отпечаток безопасным способом с ожидаемым для нового rescue-узла. Если уже сохранённый host key внезапно изменился, остановись и проверь причину, а не удаляй запись из `known_hosts` автоматически.

## 5. После SSH: только read-only диагностика

После успешного входа выполни и сохрани фактические выводы и exit codes:

~~~bash
hostname
uptime
uname -a
ip -br address
ip route
tailscale status
tailscale ip -4
lsblk -o NAME,PATH,TYPE,TRAN,RM,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINTS
findmnt
swapon --show
~~~

Состояние SSH/Tailscale-служб проверяй только под тем способом запуска, который реально используется в rescue-образе. Не предполагай, что `systemctl` или OpenSSH server присутствуют в минимальной initramfs/live-среде.

**Не выполнять:** `fsck -y`, `chkdsk /f`, запись в EFI, восстановление загрузчика, форматирование, изменение таблицы разделов, монтирование внутренних разделов read-write и другие repair-действия. Сначала выяснить, виден ли внутренний SSD/HDD, какие разделы и файловые системы существуют, и доступен ли нужный набор данных.

## 6. Если соединение не работает

Определи один конкретный слой отказа:

- **Rescue-узла нет в `tailscale status`:** загрузка/сеть/регистрация ещё не подтверждены. Попроси с места фото текущего экрана или сделай одно необходимое физическое действие.
- **Узел виден, но `tailscale ping` не проходит:** проверить фактические статусы сети и Tailscale по логам rescue-среды.
- **Tailscale ping проходит, SSH не работает:** проверить фактический SSH-метод, имя пользователя, listener/службу и auth/host-key ошибку.
- **Rescue-система не загрузилась:** записать конкретное сообщение BIOS/экрана, затем проверить уже существующий ISO и физический носитель. Не пересобирать автоматически без причины.
- **В образе действительно не настроен рабочий удалённый канал:** подготовить минимальное исправление и отдельный ISO-кандидат, сохранив known-good baseline. Повторная запись на USB — отдельное подтверждаемое действие.

Не просить владельца делать общий набор диагностик вручную, если Hermes может выполнить их через SSH. Не говорить «SSH работает» без успешного реального входа и результата команды.

## 7. Если ISO всё-таки нужно записать повторно

**Этот раздел — только запасной маршрут. Применяй его, только если доказано, что текущая флешка отсутствует, повреждена или содержит неподходящий ISO.**

Сначала установить точный ISO и его SHA-256:

~~~bash
ISO="$HOME/projects/acer-rescue-usb/build/acer-rescue-v6-final.iso"
test -f "$ISO" || { echo "ISO не найден"; exit 1; }
stat "$ISO"
sha256sum "$ISO"
~~~

Найти устройство чтением:

~~~bash
lsblk -o NAME,PATH,TYPE,TRAN,RM,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINTS
findmnt
swapon --show
~~~

Сверить USB по модели, serial, размеру, транспорту и разделам. Использовать устойчивый путь `/dev/disk/by-id/usb-...` без суффикса `-partN`, если он доступен. Убедиться, что это не системный диск, не root, не swap и не любой диск с неясным назначением.

Перед записью сообщить владельцу **конкретные** параметры:
- модель, serial, размер и полный путь целевого устройства;
- разделы/mount points и что все данные на нём будут уничтожены;
- абсолютный путь ISO, размер и SHA-256;
- точную команду записи.

Остановиться и получить явное подтверждение этой операции. До подтверждения не запускать `dd`, `ddrescue`, `wipefs`, `mkfs`, `parted`, `sgdisk`, и не размонтировать разделы. Не выбирать диск автоматически по одному `RM=1` или `/dev/sdX`.

После точного подтверждения и повторной проверки устройства:

~~~bash
# Только после явного подтверждения конкретного USB и ISO!
sudo umount <ТОЧНЫЙ_ПУТЬ_КАЖДОГО_СМОНТИРОВАННОГО_РАЗДЕЛА_ЭТОГО_USB>
sudo dd if="$ISO" of="<ПОДТВЕРЖДЁННЫЙ_ПУТЬ_USB>" bs=4M status=progress conv=fsync
sync
~~~

Подставить точные пути по результатам проверки; не выполнять строку с заполнителями. После записи безопасно сравнить первые `$(stat -c '%s' "$ISO")` байт исходного ISO и устройства командой `sudo cmp -n "$(stat -c '%s' "$ISO")" "$ISO" "<ПОДТВЕРЖДЁННЫЙ_ПУТЬ_USB>"`. Нулевой exit code подтверждает побайтовое совпадение записанного диапазона, но не доказывает физическую загрузку. Не перезаписывать known-good baseline ISO.

## 8. Что фиксировать в индексе проекта

Каноническая запись результата должна содержать только короткие факты:
- ISO path/size/SHA-256 и основание выбора;
- подтверждена ли загрузка с физического USB;
- появился ли rescue-узел в tailnet;
- результат Tailscale ping и SSH, реальные команды/exit codes;
- результаты read-only `lsblk` и список видимых разделов (не публиковать serial/секреты в публичный Git);
- следующий конкретный шаг или точный блокер.

Шаблон итогового статуса:

~~~text
STATUS: CONNECTED / PARTIAL / BLOCKED
ISO: path, size, SHA-256
Physical USB boot: PASS / FAIL / NOT TESTED + evidence
Tailscale node: confirmed name/IP or NOT SEEN
Tailscale ping: PASS / FAIL / NOT RUN
SSH: PASS / FAIL / NOT RUN + exit code
Internal disk: detected/read-only; no writes performed
Evidence location:
Single next action:
~~~

См. также [Local Verified Learning Loop](../LOCAL-VERIFIED-LEARNING-LOOP-RU.md): урок фиксируется как результат реальной работы, но запись урока не заменяет выполнение задачи и повторную проверку.
