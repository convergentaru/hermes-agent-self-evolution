# Prompt 07 — Autonomous Project Atlas, memory audit, skills and ecosystem synergy

## Mission

Work as an autonomous AI engineer, researcher, systems architect and coordinator—not as a passive command executor. Understand the full technical ecosystem, identify how projects can reinforce one another, audit existing skills and memory, and produce evidence-based recommendations.

**This phase is read-only for existing projects and memory.** You may inspect files, documentation, configuration, Git history, run safe read-only checks, test non-mutating capabilities, and write analytical reports to the designated `convergentaru/ai-control-center` repository if available. Do not alter working projects, install packages, change configurations, delete or migrate memory, publish unrelated code, or modify other repositories without approval.

## 2. Inventory real capabilities

Inspect your actual tool definitions, instructions and installed skills. Investigate file search/read, GitHub and Git, Chrome extension/browser control, YouTube workflows including non-browser methods, web extraction, audio/video transcription, memory retrieval, GBrain, Obsidian/wiki, local archives, schedulers/automation, code testing, multi-agent delegation, local models and inference services.

For each relevant capability record: purpose, source/documentation path, invocation method, installed/available status, whether practically verified, limitations, dependencies, and projects that could reuse it.

Do not claim a tool is missing before checking installed skills, documentation and viable alternatives. Do not reinstall a working tool or create a duplicate just because it was overlooked. Do not execute unknown third-party scripts or use elevated privileges without explicit approval.

## 3. Research all projects deeply

Use Atlas as an index, not as truth. Find accessible local projects, GitHub repositories, working directories, documentation, configs, tests, scripts, notes and knowledge stores. For each project inspect more than its README: examine important source files, launch instructions, configuration, tests and Git state where safe.

Record its purpose, verified current status, architecture, working capabilities, unfinished work, blockers, risks, technical debt, tests, dependencies, duplicated functionality and opportunities for reuse. Track coverage as **studied**, **partially studied**, **not verified**, or **blocked**, with reasons. Never claim full review from a directory listing alone.

Continue with accessible projects if one is blocked. Avoid unnecessary progress questions; gather the available evidence first.

## 4. Find real cross-project synergy

Consider, where present, Hermes, Jarvis Linux, OpenCode and other coding agents, local models and routing, GBrain, Obsidian/wiki, GitHub, browser automation, YouTube analysis, Screenpipe, Robot Factory/LEGO, Acer Rescue USB and reusable skills/scripts. Expand the list based on evidence.

For each proposed connection explain the problem solved, existing components to reuse, data flow/interfaces, expected benefit, implementation effort, dependencies, risks, and a measurable validation test. Identify the highest-value opportunities first. Do not force projects together when a simple interface or keeping them separate is better.

## 5. Audit memory as a working system

Find and inspect Hermes memory, startup instructions, project-local memory, GBrain schema/indexing/search/integrations, Obsidian/wiki, project docs, GitHub Issues/commits, and any accessible conversation archives. Establish what is loaded automatically, what requires explicit retrieval, what is indexed, what persists across sessions, and what is actually used.

Propose a practical layered architecture for:
1. session/work state;
2. project-specific context;
3. reusable engineering knowledge;
4. confirmed user preferences relevant to work;
5. decision history and rejected alternatives;
6. searchable/indexed knowledge with source links;
7. evidence archives such as reports, tests and commits.

Do not create separate databases for every layer without need. Select one canonical home for each information type and link/index it elsewhere. Track source, date/version, project, confidence and verification method. Separate facts, hypotheses and stale information.

Prepare a migration plan describing what to preserve, link, index, deduplicate, archive or verify; missing integrations; conflict/version handling; and a real end-to-end test: **save → retrieve → use the retrieved knowledge correctly**. Do not change or delete existing memory during this phase. Recommendations alone are not proof that memory works.

## 6. Audit and recommend skills

Search skill catalogues by capability, inspect skill documentation and dependencies, and verify invocation where safe. Prioritize file reading/search, GitHub/Git, Chrome extension control, YouTube without ordinary browser navigation, web extraction, transcription, memory/GBrain/Obsidian, automation and code testing.

Classify findings:
- available and verified;
- installed but not verified;
- alternatives available;
- useful to install after approval;
- blocked, with the exact reason.

For missing capabilities, compare appropriate options and give benefits, risks, dependencies and exact installation steps. Do not install or reconfigure anything in this phase. Respect access controls and tool safety policies.

## 8. Required deliverables

Produce:
- **Executive summary:** ecosystem status, most important problems, underused capabilities and five highest-value improvements.
- **Project register:** purpose, verified status, evidence, coverage, blockers, risks, next steps and links to related projects.
- **Synergy map:** a Mermaid diagram if feasible, plus ranked concrete integration opportunities.
- **Memory audit:** actual current behavior, gaps, proposed architecture and staged migration/test plan.
- **Skills audit:** verified capabilities, untested skills, alternatives, recommended installations and blockers.
- **Prioritized roadmap:** expected outcome, dependencies, effort, risk and verification test for each task.
- **Evidence log:** what was inspected, how it was verified, where results live, and what remains unknown.

Prefer a smaller number of well-supported findings over a large speculative report. Mark confidence and unknowns explicitly.

## 9. Definition of done

Success means source code and operational docs were actually inspected; key findings have evidence; real cross-project reuse opportunities were found; existing skills were not overlooked; memory was analyzed as a functioning save/retrieve/use pipeline; recommendations respect the real hardware and architecture; and existing projects/memory remain unchanged.

Do as much of the safe research as possible now. Save reports in the AI Control Center if available and permitted. If blocked, continue elsewhere and record the precise blocker. Do not report work as complete unless verified.

End with: what was actually studied; existing capabilities discovered; strongest synergy opportunities; memory findings; report links; unverified areas; and the single highest-value next step.

**Long-term objective:** develop a coherent, increasingly autonomous, well-documented engineering ecosystem while preserving human control over consequential changes.
