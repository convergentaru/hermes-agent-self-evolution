# Промпт: положить runbook в JetBrains-проект, Obsidian и индексы, затем синхронизировать

Канонический runbook в GitHub:
https://github.com/convergentaru/hermes-agent-self-evolution/blob/feat/local-verified-learning-loop/docs/runbooks/ACER-RESCUE-USB-AND-SSH-RU.md

Выполни задачу локально. **Не заканчивай ответом с инструкциями мне — сам найди пути, скопируй файл, обнови индексы и проверь синхронизацию.** Не трогай ISO или блочные устройства на этом этапе; здесь задача только документационная.

## 1. Установить локальные пути и исходное состояние

1. Найди локальный checkout `hermes-agent-self-evolution` и проверь ветку/commit.
2. Найди проект `~/projects/acer-rescue-usb`; выполни `git status --short`, проверь существующие папки `docs/`, README/current-state и remote. Не перезаписывай пользовательские изменения.
3. Найди Obsidian vault по реальной конфигурации Obsidian и проверь `~/robot-factory-os` как известный кандидат. Не полагайся только на предположение о пути.
4. Найди текущие project hub/index файлы: README, `docs/current-state.md`, MOC/Index, инструкции для JetBrains и GBrain. Не создавать новый параллельный индекс, если уже есть подходящий.
5. Проверь версии/поддержанные команды GBrain через `--help`/локальную документацию. Не выдумывай интерфейс команды.

## 2. Взять один канонический файл

Загрузи файл по указанному GitHub URL или используй актуальную локальную копию, сверенную с GitHub. Сохрани без смысловых изменений и перевода.

Канонический Markdown:
`docs/runbooks/ACER-RESCUE-USB-AND-SSH-RU.md`

Этот runbook различает три состояния:
- ISO ещё не записан — процедура записи с защитой от выбора неправильного диска;
- ISO уже записан — не перезаписывать без доказанного дефекта;
- текущий практический шаг — загрузить удалённый Acer с USB и подключиться по Tailscale/SSH для read-only диагностики.

## 3. JetBrains-проект

Помести идентичную копию в:
`~/projects/acer-rescue-usb/docs/runbooks/ACER-RESCUE-USB-AND-SSH-RU.md`

Создай только отсутствующие каталоги. Если целевой файл уже существует и отличается, не перезаписывай молча: сохрани копию/diff и объедини изменения так, чтобы пользовательский материал не потерялся. Поскольку JetBrains открывает этот проект как каталог, Markdown-файл должен быть виден в дереве проекта без дополнительной настройки IDE.

Добавь ссылку на runbook в существующий README или индекс проекта. Не добавляй в публичную документацию локальные Tailscale IP, serial, SSH credentials, private keys, auth URL или персональные пути с секретами.

## 4. Obsidian vault

Скопируй тот же документ в существующую папку проекта Acer Rescue USB внутри настоящего Obsidian vault. Сначала найди действующую структуру/названия папок, не создавай второй vault и не придумывай новую структуру.

Если в vault уже есть заметка-хаб Acer Rescue USB, обнови её. Если нет — создай одну понятную заметку-хаб с:
- ссылкой на runbook;
- коротким текущим статусом: «ISO по сообщению владельца уже записан; следующий шаг — загрузить Acer с USB и проверить Tailscale/SSH»;
- ссылками на проект JetBrains/GitHub;
- единственным следующим действием.

Добавь ссылку на хаб в уже существующий Obsidian home/index (`README.md`, `docs/obsidian-home.md` или фактически найденный индекс). Не создавай дубликаты, если такая ссылка уже есть.

## 5. GBrain / индекс знаний

Используй только уже установленный GBrain (иногда называвшийся в заметках FreeBrain) и его **реальную** документацию/CLI. Если у него есть поддержанный механизм индексировать выбранный Markdown-файл, добавь runbook и заметку-хаб в индекс. Не запускай полную переиндексацию истории, не загружай приватные разговоры и не перестраивай базу целиком.

Если команды индексации не удаётся подтвердить, не угадывай. Добавь ссылку в существующий Markdown-индекс как минимальный рабочий вариант и напиши, что GBrain ingestion остался непроверенным.

## 6. Синхронизация Git

- Сравни SHA-256 всех копий runbook; содержимое канонической копии, JetBrains-проекта и копии Obsidian должно совпадать.
- В каждом Git-репозитории проверь текущий branch/status до изменений.
- Добавляй в commit только runbook и конкретные изменённые индексные файлы. Никогда не используй `git add .` и не включай сторонние изменения.
- Перед push проверь remote URL/ветку/доступ; не делай force push и не переписывай историю. Если нужная синхронизация требует merge/rebase из-за чужих изменений, сохрани работу и остановись с точной причиной.
- Если Obsidian vault не является Git-репозиторием, оставь файлы локально; не инициализируй Git и не публикуй vault без отдельного разрешения.
- Не коммить приватные Tailscale/SSH данные, machine-local credentials, серийные номера и логи с приватной информацией.
- После push заново открой фактический GitHub URL/commit и подтверди, что файл действительно доступен.

## 7. После синхронизации — не уходить в теорию

В конце сообщи только проверенные результаты:
- точный локальный путь в JetBrains-проекте;
- точный путь в Obsidian и обновлённый индекс;
- GBrain: indexed / not available / not verified;
- SHA-256 каждой копии и совпадают ли они;
- какие файлы committed/pushed в какой репозиторий/ветку/commit;
- что не получилось синхронизировать и почему;
- единственное следующее практическое действие по rescue-проекту.

Не говори «всё синхронизировано», пока не проверил содержимое, индексы и доступность удалённого GitHub commit.
